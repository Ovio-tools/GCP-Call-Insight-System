# Failure-path matrix (Task 7.4)

The per-stage/per-component failure contract, built on the shared Task 2.2 failure model
(`src/failure-model/`) and the Task 7.3 alerting layer (`src/alerting/`). Every mapped
failure uses a catalog `error_code` (no generic `UNKNOWN`); every alert dedups via
`dedupKey(failure)`; every persisted `failure_snapshot` is the full §4 shape from
`failureSnapshot(failure)` and is written identically to `alert_events`, `processing_log`
failure rows, and `dead_letter`. `context` is sanitized to the allowlist
`{call_id, job_id, environment, stage, component}` — never transcript content or PII.

Legend — **Alert?**: Y = a deduped alert row is written at this site; DL = the alert is the
`DEAD_LETTER_CREATED` emitted by the worker on retry exhaustion; N = no stage alert (the
dead-letter path covers a transient throw). **Persists snapshot**: A = alert_events,
P = processing_log row, D = dead_letter.

Notes:

- ServiceTitan codes (`SERVICETITAN_*`) and backfill (`BACKFILL_CHECKPOINT_FAILED`),
  review-queue SLA (`REVIEW_QUEUE_STALLED`) are catalogued with full remediation + runbook
  sections ahead of their stages (Tasks 12.x / 11.x / 6.x); they inherit this contract when
  wired.
- The worker keeps the sanitized diagnostic (`failed_stage`, `attempts_made`, `error_name`)
  in `processing_log.detail` and `dead_letter.last_error`; the `failure_snapshot` column is
  always the clean §4 shape so all three sinks share one schema.
