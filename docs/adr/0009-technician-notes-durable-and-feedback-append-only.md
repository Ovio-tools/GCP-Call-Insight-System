# ADR 0009 — Technician notes are durable; note feedback is append-only and free-text-free

Status: accepted
Date: 2026-08-06
Relates to: ADR 0002 (redaction tokens / fail closed), ADR 0003 (no confidence scores),
ADR 0005 (reviewed decisions to labeled examples), migration
`1782864100005_technician_notes_and_note_feedback`

## Context

The extract stage produces `structured_knowledge`: what the call was about. That is the right
record for search and reporting, but it is not what a plumbing technician needs before a visit.
Reading it, a technician still does not know whether water is running right now, whether the person
who called can approve the work, what was already promised on the phone, or which of those things
the call never established at all.

`technician_notes` is that second, job-readiness record: one current note per call, generated by a
later model stage from the redacted transcript. `note_feedback` is how its quality gets measured —
a reviewer marks one field correct, wrong, missing, or shouldn't-be-here.

Two questions had to be settled before any of it was built, because both are expensive to change
after rows exist.

## Decision 1 — `technician_notes` is a durable store, never purged

`technician_notes` is registered with **no** retention group. It sits beside `structured_knowledge`
as a permanent, de-identified asset.

**Why.** The retention model draws its line at proximity to raw customer data, not at age. Raw
transcripts and the vault are purged because they are the original words. `clean_transcripts` and
`extraction_candidates` are purged because they are one step from them. A technician note is neither:
it is derived, controlled-vocabulary knowledge that has already crossed the redaction boundary and
been through the same residual scan as every other model output. It carries no transcript text and
no vault values. Deleting it would destroy operational history — how a property's plumbing was
described, what has been tried before — without reducing privacy exposure, because the sensitive
originals are already gone by then on their own clock.

Most of the schema is structurally incapable of holding free text at all. The four
question-shaped groups (`water_status`, `payer_authority`, `prior_work`, `commitments_made`) are
nullable **booleans**, not values. `commitments_made.price_quoted` records that a price was quoted,
never the amount; `commitments_made.technician_named` records that someone was named, never the
name. Only five narrative fields carry prose, and they are written from the redacted transcript.

**The reversal is cheap on purpose.** The table still carries the full retention triplet
(`retention_eligible_at`, `soft_deleted_at`, `hard_deleted_at`) and pre-provisioned column-scoped
`purge_role` grants, both dormant. If this decision is ever revisited, the change is a one-line
registration in `src/retention/purge.ts` — not a migration against a populated table.

**Guarded, not just documented.** `test/db/technician-notes-no-purge-group.test.ts` asserts both
that neither table name appears anywhere in `src/retention/purge.ts` and that a real dry-run reports
zero rows for them. Registering the table means deleting a test on purpose.

## Decision 2 — `note_feedback` is append-only, with no free-text column

A verdict is never updated or deleted. A reviewer who changes their mind inserts a new row, and the
latest row per `(call_id, field_path, reviewer_actor, note_prompt_version)` wins at read time.
`corrected_enum_value` is constrained **per field path**: `scope_signal` and `occupancy` accept only
their own vocabularies, the sixteen boolean paths accept only `'true'`/`'false'`, and every
free-text path accepts nothing but NULL.

**Why append-only.** Accuracy over time is the point of the table. An updatable verdict silently
rewrites history — you could no longer tell whether a reviewer's first read of a note was right,
which is exactly the measurement the table exists to support. Scoping every verdict to the
`note_prompt_version` it was given against matters for the same reason: a verdict on a v1 note says
nothing about a v2 note, so accuracy is only ever measured within a version.

**Why no free text.** This is the same call `src/review/correction-constants.ts` already makes for
`correct_extraction`, and it is made here for the same reason: residual PII scanning catches a great
deal but is not a complete guarantee, so a box a human can type anything into is a box that can
carry a customer's name into a store that is never purged. Under Decision 1 that combination is
permanent, which makes the free-text box strictly worse here than anywhere else in the system.

A reviewer who needs to say something in words does so outside the system. That is a real cost —
some nuance is lost — and it is accepted deliberately.

**Enforced in the database, not only in zod.** The per-field-path rule is a CHECK constraint as well
as a `superRefine`. Application-layer validation protects the application path; the constraint also
protects against a one-off script, a manual fix, or a future surface that forgets. The
`corrected_enum_value IS NULL` disjunct leads the CHECK and `field_path` is NOT NULL, so every
remaining branch evaluates to a real TRUE/FALSE — no NULL-is-satisfied hole.

## Consequences

- Technician notes accumulate indefinitely. They are small, per-call, and content-bounded; growth is
  linear in call volume, the same as `structured_knowledge`.
- A caller deleted from `call_state` takes its note and feedback with it (`ON DELETE CASCADE`).
  This differs from `structured_knowledge` (RESTRICT) on purpose — that row is the business asset a
  delete must not silently remove, whereas a note is regenerable from it.
- Reviewer feedback can express _that_ something is wrong and, for controlled fields, _what it
  should be_ — but never _why_. If the "why" turns out to be necessary, the honest fix is a new
  controlled vocabulary of reasons, not a text column.
- Both vocabularies live twice: as `as const` tuples in `src/db/enums.ts` and as CHECK lists in the
  migration (the CommonJS/ESM split makes sharing impractical, per `DROP_REASONS`).
  `test/db/note-vocabulary-parity.test.ts` reads the live constraint definitions and fails on drift.
